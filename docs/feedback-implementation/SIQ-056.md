# SIQ-056 — Reduce the Trip flow to 3–5 meaningful steps

## Ticket

- ID: SIQ-056
- Comment: Reduce the Trip flow to 3–5 meaningful steps
- Scope: Specific Screen
- Screen / Product Area: Trips
- Size: Large
- Workstream: Trips
- Original Description: Combine destination/date entry, context, generation, packing list, and outfits while keeping advanced editing optional.

## Problem

The current `0.html` prototype exposes this area through J-01–J-14 collapsed into combined input/context and J-14 hub. The relevant rendering/routing surface is `screens registry, renderScreen, go, tripScreenV2`.

Current behavior is partially represented, but the ticket acceptance is not proven end to end. The existing architecture still exposes feature-oriented routes and, where applicable, separate configuration, processing, or result states. No dedicated `0.html` regression evidence currently closes SIQ-056.

## UX Decision

- Collapse destination, luggage, must-haves, activities, building, review, suggested items, looks, and creation into a lean Trip flow.
- Recommended shape: destination/dates → context → generated Trip hub (Packing | Outfits), with optional advanced edit.
- Do not remove capabilities; relocate them into the hub/sheets.
- Preserve saved Trip editing after creation.

The decision must preserve the existing editorial/liquid-material direction, reduce decisions and nested screens, and reuse canonical state rather than creating a parallel feature.

## Current Flow

`J-01 → J-02 → J-04/J-05/J-06 → J-07 → J-08/J-09/J-10 → J-13 → J-14.`

## Target Flow

`Current context → Reduce the Trip flow to 3–5 meaningful steps → immediate useful result or primary action → optional edit/sheet only when needed.`

Use a full screen only for a distinct user job. Prefer direct action, inline state, one shared bottom sheet, background work, or progressive disclosure for intermediate steps.

## Affected Screens

- Audit/change: J-01–J-14 collapsed into combined input/context and J-14 hub
- Retain until replacement passes: all existing entry, back, cancel, empty, and error paths around those screens.
- Remove/merge only after the replacement journey is verified.
- New standalone route: not assumed; first attempt to solve inside the mapped canonical surface.

## Technical Impact

- HTML/CSS/JS baseline: `0.html`
- Functions/routes: `screens registry, renderScreen, go, tripScreenV2`
- Shared UI: `shell`, root/bottom navigation, reusable sheet/overlay patterns, image components, and accessibility labels.
- State: reuse the relevant canonical prototype state; do not fork Closet, Look, Canvas, Planner, Trip, Twin, Lens, or Muse data.
- Persistence: the baseline has no canonical localStorage model; add persistence only when this ticket explicitly requires it and test migration/reset behavior.
- Tests: add/extend dedicated Playwright coverage for `0.html` on desktop and 375×812 mobile.
