# SIQ-018 — Shorten onboarding aggressively

## Ticket

- ID: SIQ-018
- Comment: Shorten onboarding aggressively
- Scope: Specific Screen
- Screen / Product Area: Onboarding
- Size: Foundation
- Workstream: Onboarding
- Original Description: Keep only information needed to begin using StyleIQ and defer optional profile-building tasks until they become relevant.

## Problem

The current `0.html` prototype exposes this area through S-00–S-02 and A-01–A-15 first-use route. The relevant rendering/routing surface is `screens registry, renderScreen, go, onboarding`.

Current behavior is partially represented, but the ticket acceptance is not proven end to end. The existing architecture still exposes feature-oriented routes and, where applicable, separate configuration, processing, or result states. No dedicated `0.html` regression evidence currently closes SIQ-018.

## UX Decision

- Redesign required onboarding around the minimum information needed to reach useful styling value.
- Audit Splash, Muse intro, account access, wardrobe context, Style Twin, attribution, brands, and first Closet setup.
- Move optional setup to contextual moments after the user reaches the product.
- Target a journey that can reach Today/first useful output with very few deliberate actions.

The decision must preserve the existing editorial/liquid-material direction, reduce decisions and nested screens, and reuse canonical state rather than creating a parallel feature.

## Current Flow

`S-00 → S-01 → S-02 → A-series setup screens → A-11/D-02 first value.`

## Target Flow

`Current context → Shorten onboarding aggressively → immediate useful result or primary action → optional edit/sheet only when needed.`

Use a full screen only for a distinct user job. Prefer direct action, inline state, one shared bottom sheet, background work, or progressive disclosure for intermediate steps.

## Affected Screens

- Audit/change: S-00–S-02 and A-01–A-15 first-use route
- Retain until replacement passes: all existing entry, back, cancel, empty, and error paths around those screens.
- Remove/merge only after the replacement journey is verified.
- New standalone route: not assumed; first attempt to solve inside the mapped canonical surface.

## Technical Impact

- HTML/CSS/JS baseline: `0.html`
- Functions/routes: `screens registry, renderScreen, go, onboarding`
- Shared UI: `shell`, root/bottom navigation, reusable sheet/overlay patterns, image components, and accessibility labels.
- State: reuse the relevant canonical prototype state; do not fork Closet, Look, Canvas, Planner, Trip, Twin, Lens, or Muse data.
- Persistence: the baseline has no canonical localStorage model; add persistence only when this ticket explicitly requires it and test migration/reset behavior.
- Tests: add/extend dedicated Playwright coverage for `0.html` on desktop and 375×812 mobile.
