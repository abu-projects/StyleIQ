# SIQ-014 — Remove Occupation from onboarding

## Ticket

- ID: SIQ-014
- Comment: Remove Occupation from onboarding
- Scope: Specific Screen
- Screen / Product Area: Onboarding
- Size: Small
- Workstream: Onboarding
- Original Description: Do not ask the user for their occupation as part of initial setup. StyleIQ should learn contextual dressing needs over time or ask only when relevant.

## Problem

The current `0.html` prototype exposes this area through A-05 Profile setup · Occupation. The relevant rendering/routing surface is `screens registry, renderScreen, go, onboarding`.

Current behavior is partially represented, but the ticket acceptance is not proven end to end. The existing architecture still exposes feature-oriented routes and, where applicable, separate configuration, processing, or result states. No dedicated `0.html` regression evidence currently closes SIQ-014.

## UX Decision

- Remove the Occupation step from the required onboarding journey.
- Remove any dependent Continue/back routing and onboarding progress count.
- Keep occupation out of required Profile completion as well unless a later product decision explicitly requires it.
- If contextual dressing information is needed, collect it later from real events/behavior.

The decision must preserve the existing editorial/liquid-material direction, reduce decisions and nested screens, and reuse canonical state rather than creating a parallel feature.

## Current Flow

`S-00 → S-01 → S-02 → A-series setup screens → A-11/D-02 first value.`

## Target Flow

`Current context → Remove Occupation from onboarding → immediate useful result or primary action → optional edit/sheet only when needed.`

Use a full screen only for a distinct user job. Prefer direct action, inline state, one shared bottom sheet, background work, or progressive disclosure for intermediate steps.

## Affected Screens

- Audit/change: A-05 Profile setup · Occupation
- Retain until replacement passes: all existing entry, back, cancel, empty, and error paths around those screens.
- Remove/merge only after the replacement journey is verified.
- New standalone route: not assumed; first attempt to solve inside the mapped canonical surface.

## Technical Impact

- HTML/CSS/JS baseline: `0.html`
- Functions/routes: `screens registry, renderScreen, go, onboarding`
- Shared UI: `shell`, root/bottom navigation, reusable sheet/overlay patterns, image components, and accessibility labels.
- State: reuse the relevant canonical prototype state; do not fork Closet, Look, Canvas, Planner, Trip, Twin, Lens, or Muse data.
- Persistence: the baseline has no canonical localStorage model; add persistence only when this ticket explicitly requires it and test migration/reset behavior.
- Tests: add/extend dedicated Playwright coverage for `0.html` on desktop and 375×812 mobile.
