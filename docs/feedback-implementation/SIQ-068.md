# SIQ-068 — Treat the current color palette as provisional

## Ticket

- ID: SIQ-068
- Comment: Treat the current color palette as provisional
- Scope: General
- Screen / Product Area: Visual Design
- Size: Foundation
- Workstream: Visual System Constraints
- Original Description: The current colors are not approved. Keep color usage tokenized and easy to update without affecting layout, hierarchy, components, or UX decisions.

## Problem

The current `0.html` prototype exposes this area through `:root` CSS tokens and every new component color. The relevant rendering/routing surface is `screens registry, renderScreen, go`.

Current behavior is partially represented, but the ticket acceptance is not proven end to end. The existing architecture still exposes feature-oriented routes and, where applicable, separate configuration, processing, or result states. No dedicated `0.html` regression evidence currently closes SIQ-068.

## UX Decision

- Do not hard-code new feature colors ad hoc.
- Centralize colors through existing design tokens/CSS variables.
- Ensure new components can inherit a future approved palette without structural rework.
- Do not present current color choices as client-approved.

The decision must preserve the existing editorial/liquid-material direction, reduce decisions and nested screens, and reuse canonical state rather than creating a parallel feature.

## Current Flow

`The screen index exposes the capability through feature-specific routes, often with separate full-screen configuration, processing, and result states.`

## Target Flow

`Current context → Treat the current color palette as provisional → immediate useful result or primary action → optional edit/sheet only when needed.`

Use a full screen only for a distinct user job. Prefer direct action, inline state, one shared bottom sheet, background work, or progressive disclosure for intermediate steps.

## Affected Screens

- Audit/change: `:root` CSS tokens and every new component color
- Retain until replacement passes: all existing entry, back, cancel, empty, and error paths around those screens.
- Remove/merge only after the replacement journey is verified.
- New standalone route: not assumed; first attempt to solve inside the mapped canonical surface.

## Technical Impact

- HTML/CSS/JS baseline: `0.html`
- Functions/routes: `screens registry, renderScreen, go`
- Shared UI: `shell`, root/bottom navigation, reusable sheet/overlay patterns, image components, and accessibility labels.
- State: reuse the relevant canonical prototype state; do not fork Closet, Look, Canvas, Planner, Trip, Twin, Lens, or Muse data.
- Persistence: the baseline has no canonical localStorage model; add persistence only when this ticket explicitly requires it and test migration/reset behavior.
- Tests: add/extend dedicated Playwright coverage for `0.html` on desktop and 375×812 mobile.

Constraint for all visual implementation.
