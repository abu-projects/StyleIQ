# SIQ-021 — Reduce Continue-driven workflows

## Ticket

- ID: SIQ-021
- Comment: Reduce Continue-driven workflows
- Scope: General
- Screen / Product Area: Whole Product
- Size: Foundation
- Workstream: Product Simplification Foundation
- Original Description: Avoid repetitive Continue buttons. Use direct selection, auto-advance, one-tap approval, inline actions, and contextual completion whenever the next action is obvious.

## Problem

The current `0.html` prototype exposes this area through All generic Continue/Next actions across S/A/B/H/I/J. The relevant rendering/routing surface is `screens registry, renderScreen, go`.

Current behavior is partially represented, but the ticket acceptance is not proven end to end. The existing architecture still exposes feature-oriented routes and, where applicable, separate configuration, processing, or result states. No dedicated `0.html` regression evidence currently closes SIQ-021.

## UX Decision

- Audit every Continue/Next button in the prototype.
- Remove buttons where selection can auto-advance safely or where the action itself already expresses intent.
- Replace generic Continue labels with meaningful actions when a button is truly needed.
- Keep explicit confirmation only for destructive, privacy-sensitive, or high-impact operations.

The decision must preserve the existing editorial/liquid-material direction, reduce decisions and nested screens, and reuse canonical state rather than creating a parallel feature.

## Current Flow

`The screen index exposes the capability through feature-specific routes, often with separate full-screen configuration, processing, and result states.`

## Target Flow

`Current context → Reduce Continue-driven workflows → immediate useful result or primary action → optional edit/sheet only when needed.`

Use a full screen only for a distinct user job. Prefer direct action, inline state, one shared bottom sheet, background work, or progressive disclosure for intermediate steps.

## Affected Screens

- Audit/change: All generic Continue/Next actions across S/A/B/H/I/J
- Retain until replacement passes: all existing entry, back, cancel, empty, and error paths around those screens.
- Remove/merge only after the replacement journey is verified.
- New standalone route: not assumed; first attempt to solve inside the mapped canonical surface.

## Technical Impact

- HTML/CSS/JS baseline: `0.html`
- Functions/routes: `screens registry, renderScreen, go`
- Shared UI: `shell`, root/bottom navigation, reusable sheet/overlay patterns, image components, and accessibility labels.
- State: reuse the relevant canonical prototype state; do not fork Closet, Look, Canvas, Planner, Trip, Twin, Lens, or Muse data.
- Persistence: the baseline has no canonical localStorage model; add persistence only when this ticket explicitly requires it and test migration/reset behavior.
- Tests: add/extend dedicated Playwright coverage for `0.html` on desktop and 375×812 mobile.
