# SIQ-054 — Simplify Planner around user intent

## Ticket

- ID: SIQ-054
- Comment: Simplify Planner around user intent
- Scope: Specific Screen
- Screen / Product Area: Planner
- Size: Large
- Workstream: Planner
- Original Description: Instead of requiring users to complete structured event forms, ask what they are dressing for and let StyleIQ interpret the event context.

## Problem

The current `0.html` prototype exposes this area through I-01 Planner, I-03 day action, I-04/I-05 event create/validation. The relevant rendering/routing surface is `screens registry, renderScreen, go, plannerScreen / mirrorPlanner`.

Current behavior is partially represented, but the ticket acceptance is not proven end to end. The existing architecture still exposes feature-oriented routes and, where applicable, separate configuration, processing, or result states. No dedicated `0.html` regression evidence currently closes SIQ-054.

## UX Decision

- Replace form-first event creation with an intent-first entry from the selected day.
- Ask what the user is dressing for in natural language.
- Generate/structure date, occasion, dress code, and relevant context internally.
- Expose detailed fields only through Edit.

The decision must preserve the existing editorial/liquid-material direction, reduce decisions and nested screens, and reuse canonical state rather than creating a parallel feature.

## Current Flow

`I-01 → I-03 → I-04 form → I-05 validation → generated Look.`

## Target Flow

`Current context → Simplify Planner around user intent → immediate useful result or primary action → optional edit/sheet only when needed.`

Use a full screen only for a distinct user job. Prefer direct action, inline state, one shared bottom sheet, background work, or progressive disclosure for intermediate steps.

## Affected Screens

- Audit/change: I-01 Planner, I-03 day action, I-04/I-05 event create/validation
- Retain until replacement passes: all existing entry, back, cancel, empty, and error paths around those screens.
- Remove/merge only after the replacement journey is verified.
- New standalone route: not assumed; first attempt to solve inside the mapped canonical surface.

## Technical Impact

- HTML/CSS/JS baseline: `0.html`
- Functions/routes: `screens registry, renderScreen, go, plannerScreen / mirrorPlanner`
- Shared UI: `shell`, root/bottom navigation, reusable sheet/overlay patterns, image components, and accessibility labels.
- State: reuse the relevant canonical prototype state; do not fork Closet, Look, Canvas, Planner, Trip, Twin, Lens, or Muse data.
- Persistence: the baseline has no canonical localStorage model; add persistence only when this ticket explicitly requires it and test migration/reset behavior.
- Tests: add/extend dedicated Playwright coverage for `0.html` on desktop and 375×812 mobile.
