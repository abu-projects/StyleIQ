# SIQ-062 — Make intelligence contextual

## Ticket

- ID: SIQ-062
- Comment: Make intelligence contextual
- Scope: General
- Screen / Product Area: Whole Product
- Size: Foundation
- Workstream: Product Simplification Foundation
- Original Description: Do not create separate destinations merely to display “intelligence.” Surface AI insights next to the item, outfit, purchase, trip, or decision where they are useful.

## Problem

The current `0.html` prototype exposes this area through C-06 intelligence route, M-03 insight, D-02, C-02, K-04, J-14 contexts. The relevant rendering/routing surface is `screens registry, renderScreen, go, closetScreen / mirrorCloset, museScreen / enrichCoreScreens, homeScreen / mirrorToday / outfitFamilies, discoverScreen / mirrorDiscover, tripScreenV2`.

Current behavior is partially represented, but the ticket acceptance is not proven end to end. The existing architecture still exposes feature-oriented routes and, where applicable, separate configuration, processing, or result states. No dedicated `0.html` regression evidence currently closes SIQ-062.

## UX Decision

- Remove 'Intelligence' as a destination concept where it merely displays derived data.
- Move insights beside the item/outfit/purchase/trip decision they explain.
- Reuse insight cards/rows across contexts.
- Keep deeper analytics only when the user has a genuine analysis job.

The decision must preserve the existing editorial/liquid-material direction, reduce decisions and nested screens, and reuse canonical state rather than creating a parallel feature.

## Current Flow

`The screen index exposes the capability through feature-specific routes, often with separate full-screen configuration, processing, and result states.`

## Target Flow

`Current context → Make intelligence contextual → immediate useful result or primary action → optional edit/sheet only when needed.`

Use a full screen only for a distinct user job. Prefer direct action, inline state, one shared bottom sheet, background work, or progressive disclosure for intermediate steps.

## Affected Screens

- Audit/change: C-06 intelligence route, M-03 insight, D-02, C-02, K-04, J-14 contexts
- Retain until replacement passes: all existing entry, back, cancel, empty, and error paths around those screens.
- Remove/merge only after the replacement journey is verified.
- New standalone route: not assumed; first attempt to solve inside the mapped canonical surface.

## Technical Impact

- HTML/CSS/JS baseline: `0.html`
- Functions/routes: `screens registry, renderScreen, go, closetScreen / mirrorCloset, museScreen / enrichCoreScreens, homeScreen / mirrorToday / outfitFamilies, discoverScreen / mirrorDiscover, tripScreenV2`
- Shared UI: `shell`, root/bottom navigation, reusable sheet/overlay patterns, image components, and accessibility labels.
- State: reuse the relevant canonical prototype state; do not fork Closet, Look, Canvas, Planner, Trip, Twin, Lens, or Muse data.
- Persistence: the baseline has no canonical localStorage model; add persistence only when this ticket explicitly requires it and test migration/reset behavior.
- Tests: add/extend dedicated Playwright coverage for `0.html` on desktop and 375×812 mobile.
