# SIQ-064 — Make visual search a core interaction

## Ticket

- ID: SIQ-064
- Comment: Make visual search a core interaction
- Scope: General
- Screen / Product Area: Search
- Size: Large
- Workstream: StyleIQ Lens & Visual Search
- Original Description: Support searching the Closet and inspiration through images and visual similarity in addition to traditional keyword/filter controls.

## Problem

The current `0.html` prototype exposes this area through C-01 Closet, K-02 search, K-04 product/look detail, shared Lens result. The relevant rendering/routing surface is `screens registry, renderScreen, go, closetScreen / mirrorCloset, discoverScreen / mirrorDiscover`.

Current behavior is partially represented, but the ticket acceptance is not proven end to end. The existing architecture still exposes feature-oriented routes and, where applicable, separate configuration, processing, or result states. No dedicated `0.html` regression evidence currently closes SIQ-064.

## UX Decision

- Add image-based/similarity search as a shared capability for Closet, Lens, Discover, and shopping evaluation.
- Keep text search and filters, but do not make them the only discovery mechanism.
- Use visual search to surface owned alternatives before shopping.

The decision must preserve the existing editorial/liquid-material direction, reduce decisions and nested screens, and reuse canonical state rather than creating a parallel feature.

## Current Flow

`Visual jobs are split between B import, C Closet, K Discover, M Muse, and J Trips; no canonical Lens route exists.`

## Target Flow

`Current context → Make visual search a core interaction → immediate useful result or primary action → optional edit/sheet only when needed.`

Use a full screen only for a distinct user job. Prefer direct action, inline state, one shared bottom sheet, background work, or progressive disclosure for intermediate steps.

## Affected Screens

- Audit/change: C-01 Closet, K-02 search, K-04 product/look detail, shared Lens result
- Retain until replacement passes: all existing entry, back, cancel, empty, and error paths around those screens.
- Remove/merge only after the replacement journey is verified.
- New standalone route: not assumed; first attempt to solve inside the mapped canonical surface.

## Technical Impact

- HTML/CSS/JS baseline: `0.html`
- Functions/routes: `screens registry, renderScreen, go, closetScreen / mirrorCloset, discoverScreen / mirrorDiscover`
- Shared UI: `shell`, root/bottom navigation, reusable sheet/overlay patterns, image components, and accessibility labels.
- State: reuse the relevant canonical prototype state; do not fork Closet, Look, Canvas, Planner, Trip, Twin, Lens, or Muse data.
- Persistence: the baseline has no canonical localStorage model; add persistence only when this ticket explicitly requires it and test migration/reset behavior.
- Tests: add/extend dedicated Playwright coverage for `0.html` on desktop and 375×812 mobile.
