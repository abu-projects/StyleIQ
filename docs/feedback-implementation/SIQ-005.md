# SIQ-005 — Create StyleIQ Lens

## Ticket

- ID: SIQ-005
- Comment: Create StyleIQ Lens
- Scope: General
- Screen / Product Area: Global AI Entry
- Size: Foundation
- Workstream: StyleIQ Lens & Visual Search
- Original Description: Create one camera-first AI entry point that understands different visual intents instead of placing each visual capability behind a separate menu.

## Problem

The current `0.html` prototype exposes this area through NEW reusable Lens overlay/state connected to root destinations D-02, C-01, I-01, K-01, L-01. The relevant rendering/routing surface is `screens registry, renderScreen, go, homeScreen / mirrorToday / outfitFamilies, closetScreen / mirrorCloset, plannerScreen / mirrorPlanner, discoverScreen / mirrorDiscover, profileScreen / mirrorProfile`.

Current behavior is partially represented, but the ticket acceptance is not proven end to end. The existing architecture still exposes feature-oriented routes and, where applicable, separate configuration, processing, or result states. No dedicated `0.html` regression evidence currently closes SIQ-005.

## UX Decision

- Create a single visual AI entry point named StyleIQ Lens.
- Lens must accept camera, photo library, and screenshot-style inputs.
- After input, infer the user's likely intent from context and offer the smallest relevant next action.
- Build Lens as reusable architecture, not seven separate camera features.

The decision must preserve the existing editorial/liquid-material direction, reduce decisions and nested screens, and reuse canonical state rather than creating a parallel feature.

## Current Flow

`Visual jobs are split between B import, C Closet, K Discover, M Muse, and J Trips; no canonical Lens route exists.`

## Target Flow

`Current context → Create StyleIQ Lens → immediate useful result or primary action → optional edit/sheet only when needed.`

Use a full screen only for a distinct user job. Prefer direct action, inline state, one shared bottom sheet, background work, or progressive disclosure for intermediate steps.

## Affected Screens

- Audit/change: NEW reusable Lens overlay/state connected to root destinations D-02, C-01, I-01, K-01, L-01
- Retain until replacement passes: all existing entry, back, cancel, empty, and error paths around those screens.
- Remove/merge only after the replacement journey is verified.
- New state required: yes; it must be added to the canonical screen/state architecture, not as a duplicate feature.

- Functions/routes: `screens registry, renderScreen, go, homeScreen / mirrorToday / outfitFamilies, closetScreen / mirrorCloset, plannerScreen / mirrorPlanner, discoverScreen / mirrorDiscover, profileScreen / mirrorProfile`
