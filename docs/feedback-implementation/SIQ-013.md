# SIQ-013 — Lens: Find similar owned items

## Ticket

- ID: SIQ-013
- Comment: Lens: Find similar owned items
- Scope: General
- Screen / Product Area: StyleIQ Lens
- Size: Medium
- Workstream: StyleIQ Lens & Visual Search
- Original Description: When viewing a product, visually compare it against the user's existing Closet and surface similar or duplicate items.

## Problem

The current `0.html` prototype exposes this area through C-01/C-02 owned-item comparison and K-04 inline comparison. The relevant rendering/routing surface is `screens registry, renderScreen, go, closetScreen / mirrorCloset, discoverScreen / mirrorDiscover`.

Current behavior is partially represented, but the ticket acceptance is not proven end to end. The existing architecture still exposes feature-oriented routes and, where applicable, separate configuration, processing, or result states. No dedicated `0.html` regression evidence currently closes SIQ-013.

## UX Decision

- From a product image, perform visual similarity against Closet items.
- Show the closest owned alternatives with meaningful comparison dimensions.
- Use this capability inside purchase evaluation and Discover as a shared service/pattern.
- Avoid a separate full-screen flow when an inline comparison or sheet is sufficient.

The decision must preserve the existing editorial/liquid-material direction, reduce decisions and nested screens, and reuse canonical state rather than creating a parallel feature.

## Current Flow

`Visual jobs are split between B import, C Closet, K Discover, M Muse, and J Trips; no canonical Lens route exists.`

## Target Flow

`Current context → Lens: Find similar owned items → immediate useful result or primary action → optional edit/sheet only when needed.`

Use a full screen only for a distinct user job. Prefer direct action, inline state, one shared bottom sheet, background work, or progressive disclosure for intermediate steps.

## Affected Screens

- Audit/change: C-01/C-02 owned-item comparison and K-04 inline comparison
- Retain until replacement passes: all existing entry, back, cancel, empty, and error paths around those screens.
- Remove/merge only after the replacement journey is verified.
- New standalone route: not assumed; first attempt to solve inside the mapped canonical surface.
