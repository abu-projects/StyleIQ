# SIQ-049 — Keep advanced Create mode optional

## Ticket

- ID: SIQ-049
- Comment: Keep advanced Create mode optional
- Scope: Specific Screen
- Screen / Product Area: Style Studio
- Size: Large
- Workstream: Style Studio
- Original Description: Retain deeper canvas, drag-and-drop, and advanced editing capabilities for users who actively choose a more powerful Create mode.

## Problem

The current `0.html` prototype exposes this area through F-01–F-11 advanced Create mode sharing one canvasState. The relevant rendering/routing surface is `screens registry, renderScreen, go, studioScreen / mirrorStudioV2`.

Current behavior is partially represented, but the ticket acceptance is not proven end to end. The existing architecture still exposes feature-oriented routes and, where applicable, separate configuration, processing, or result states. No dedicated `0.html` regression evidence currently closes SIQ-049.

## UX Decision

- Preserve deeper canvas/drag/reorder/multi-layer capabilities behind an explicit advanced Create mode.
- Do not require advanced mode to complete common outfit edits.
- Share the same canonical Look state between Simple and Create modes.
- Switching modes must not lose draft changes.

The decision must preserve the existing editorial/liquid-material direction, reduce decisions and nested screens, and reuse canonical state rather than creating a parallel feature.

## Current Flow

`F-01 → technical layer/category/manual-selection screens → save.`

## Target Flow

`Current context → Keep advanced Create mode optional → immediate useful result or primary action → optional edit/sheet only when needed.`

Use a full screen only for a distinct user job. Prefer direct action, inline state, one shared bottom sheet, background work, or progressive disclosure for intermediate steps.

## Affected Screens

- Audit/change: F-01–F-11 advanced Create mode sharing one canvasState
- Retain until replacement passes: all existing entry, back, cancel, empty, and error paths around those screens.
- Remove/merge only after the replacement journey is verified.
- New standalone route: not assumed; first attempt to solve inside the mapped canonical surface.

## Technical Impact

- HTML/CSS/JS baseline: `0.html`
- Functions/routes: `screens registry, renderScreen, go, studioScreen / mirrorStudioV2`
- Shared UI: `shell`, root/bottom navigation, reusable sheet/overlay patterns, image components, and accessibility labels.
- State: reuse the relevant canonical prototype state; do not fork Closet, Look, Canvas, Planner, Trip, Twin, Lens, or Muse data.
- Persistence: the baseline has no canonical localStorage model; add persistence only when this ticket explicitly requires it and test migration/reset behavior.
- Tests: add/extend dedicated Playwright coverage for `0.html` on desktop and 375×812 mobile.
