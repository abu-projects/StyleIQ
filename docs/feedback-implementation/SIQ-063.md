# SIQ-063 — Design around user jobs instead of features

## Ticket

- ID: SIQ-063
- Comment: Design around user jobs instead of features
- Scope: General
- Screen / Product Area: Product Architecture
- Size: Foundation
- Workstream: Product Simplification Foundation
- Original Description: Users should be able to express goals such as Dress Me, Should I Buy This, Recreate This, Help Me Pack, or What Goes With This, while StyleIQ orchestrates the required features internally.

## Problem

The current `0.html` prototype exposes this area through Root jobs across D/C/I/J/K/L orchestrated through Lens and Muse. The relevant rendering/routing surface is `screens registry, renderScreen, go`.

Current behavior is partially represented, but the ticket acceptance is not proven end to end. The existing architecture still exposes feature-oriented routes and, where applicable, separate configuration, processing, or result states. No dedicated `0.html` regression evidence currently closes SIQ-063.

## UX Decision

- Use user goals such as Dress Me, Should I Buy This, Recreate This, Help Me Pack, and What Goes With This as the interaction model.
- Let Lens and Muse orchestrate underlying features.
- Reduce the need for users to know which internal feature owns a task.
- Use this principle when deciding whether existing navigation/screen boundaries should remain.

The decision must preserve the existing editorial/liquid-material direction, reduce decisions and nested screens, and reuse canonical state rather than creating a parallel feature.

## Current Flow

`The screen index exposes the capability through feature-specific routes, often with separate full-screen configuration, processing, and result states.`

## Target Flow

`Current context → Design around user jobs instead of features → immediate useful result or primary action → optional edit/sheet only when needed.`

Use a full screen only for a distinct user job. Prefer direct action, inline state, one shared bottom sheet, background work, or progressive disclosure for intermediate steps.

## Affected Screens

- Audit/change: Root jobs across D/C/I/J/K/L orchestrated through Lens and Muse
- Retain until replacement passes: all existing entry, back, cancel, empty, and error paths around those screens.
- Remove/merge only after the replacement journey is verified.
- New standalone route: not assumed; first attempt to solve inside the mapped canonical surface.

## Technical Impact

- HTML/CSS/JS baseline: `0.html`
- Functions/routes: `screens registry, renderScreen, go`
- Shared UI: `shell`, root/bottom navigation, reusable sheet/overlay patterns, image components, and accessibility labels.
- State: reuse the relevant canonical prototype state; do not fork Closet, Look, Canvas, Planner, Trip, Twin, Lens, or Muse data.
- Persistence: the baseline has no canonical localStorage model; add persistence only when this ticket explicitly requires it and test migration/reset behavior.
- Tests: add/extend dedicated Playwright coverage for `0.html` on desktop and 375×812 mobile.
