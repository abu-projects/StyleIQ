# SIQ-001 — Make the overall product significantly leaner

## Ticket

- ID: SIQ-001
- Comment: Make the overall product significantly leaner
- Scope: General
- Screen / Product Area: Whole Product
- Size: Foundation
- Workstream: Product Simplification Foundation
- Original Description: Reduce unnecessary screens, steps, decisions, and setup across all StyleIQ flows. The goal is faster value, not simply fewer screens.

## Problem

The current `0.html` prototype exposes this area through All registered screens S-00–M-03; especially onboarding A-01–A-15, import B-01–B-11, actions E-01–E-06, Twin H-01–H-10, Planner I-01–I-06, Trips J-01–J-14. The relevant rendering/routing surface is `screens registry, renderScreen, go, museScreen / enrichCoreScreens, onboarding, importScreen / mirrorItemUpload, actionScreen, avatarScreen / mirrorTwinIntro / mirrorUpload, plannerScreen / mirrorPlanner, tripScreenV2`.

Current behavior is partially represented, but the ticket acceptance is not proven end to end. The existing architecture still exposes feature-oriented routes and, where applicable, separate configuration, processing, or result states. No dedicated `0.html` regression evidence currently closes SIQ-001.

## UX Decision

- Audit the whole prototype for flows where a single user job is represented by several screens or explicit Continue/Confirm steps.
- Create a simplification map before deleting anything: keep the capability, reduce the surface.
- Convert intermediate states into inline state, bottom sheets, overlays, loading states, or background processing where appropriate.
- Do not use screen-count reduction as the only success metric; measure user decisions and interactions required for core jobs.

The decision must preserve the existing editorial/liquid-material direction, reduce decisions and nested screens, and reuse canonical state rather than creating a parallel feature.

## Current Flow

`The screen index exposes the capability through feature-specific routes, often with separate full-screen configuration, processing, and result states.`

## Target Flow

`Current context → Make the overall product significantly leaner → immediate useful result or primary action → optional edit/sheet only when needed.`

Use a full screen only for a distinct user job. Prefer direct action, inline state, one shared bottom sheet, background work, or progressive disclosure for intermediate steps.

## Affected Screens

- Audit/change: All registered screens S-00–M-03; especially onboarding A-01–A-15, import B-01–B-11, actions E-01–E-06, Twin H-01–H-10, Planner I-01–I-06, Trips J-01–J-14
- Retain until replacement passes: all existing entry, back, cancel, empty, and error paths around those screens.
- Remove/merge only after the replacement journey is verified.
- New standalone route: not assumed; first attempt to solve inside the mapped canonical surface.

- Functions/routes: `screens registry, renderScreen, go, museScreen / enrichCoreScreens, onboarding, importScreen / mirrorItemUpload, actionScreen, avatarScreen / mirrorTwinIntro / mirrorUpload, plannerScreen / mirrorPlanner, tripScreenV2`

#### Guardrails established

- Public route contract: every registered hash must resolve without a runtime error or broken image.
- One-screen contract: a route renders one `.screen`; lightweight secondary UI must remain a sheet, aside, or overlay rather than another nested screen.
- Canonical root contract: Today, Closet, Planner, and Discover stay connected through one primary navigation; secondary jobs stay accessible through More.
- Replacement contract: legacy routes remain until their new path passes happy, back, dismiss, mobile, and desktop checks.
- Visual observation: the current mobile Today bottom navigation sits over the lower action region, and the Add Photos continuation is below the initial fold. These are recorded inputs for the reusable spacing/sheet work in SIQ-001.2, not approved regressions.
