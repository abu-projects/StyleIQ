# SIQ-033 — Surface lifecycle collections in the Closet

## Ticket

- ID: SIQ-033
- Comment: Surface lifecycle collections in the Closet
- Scope: Specific Screen
- Screen / Product Area: Closet
- Size: Medium
- Workstream: Closet & Photo Import
- Original Description: Provide easy access to grouped item states such as Favorites, Underused, Won't Wear, Sell, Donate, Rent, and Archived.

## Problem

The current `0.html` prototype exposes this area through C-01 Closet smart collections. The relevant rendering/routing surface is `screens registry, renderScreen, go, closetScreen / mirrorCloset`.

Current behavior is partially represented, but the ticket acceptance is not proven end to end. The existing architecture still exposes feature-oriented routes and, where applicable, separate configuration, processing, or result states. No dedicated `0.html` regression evidence currently closes SIQ-033.

## UX Decision

- Create smart collections based on lifecycle/status state.
- Show counts and easy access for Favorites, Underused, Won't Wear, Sell, Donate, Rent, Archived as approved.
- Do not copy items into separate data stores; derive collections from the canonical item.

The decision must preserve the existing editorial/liquid-material direction, reduce decisions and nested screens, and reuse canonical state rather than creating a parallel feature.

## Current Flow

`C-01 → C-02 → separate C-03/C-04/C-05/C-06/C-07 screens.`

## Target Flow

`Current context → Surface lifecycle collections in the Closet → immediate useful result or primary action → optional edit/sheet only when needed.`

Use a full screen only for a distinct user job. Prefer direct action, inline state, one shared bottom sheet, background work, or progressive disclosure for intermediate steps.

## Affected Screens

- Audit/change: C-01 Closet smart collections
- Retain until replacement passes: all existing entry, back, cancel, empty, and error paths around those screens.
- Remove/merge only after the replacement journey is verified.
- New standalone route: not assumed; first attempt to solve inside the mapped canonical surface.

## Technical Impact

- HTML/CSS/JS baseline: `0.html`
- Functions/routes: `screens registry, renderScreen, go, closetScreen / mirrorCloset`
- Shared UI: `shell`, root/bottom navigation, reusable sheet/overlay patterns, image components, and accessibility labels.
- State: reuse the relevant canonical prototype state; do not fork Closet, Look, Canvas, Planner, Trip, Twin, Lens, or Muse data.
- Persistence: the baseline has no canonical localStorage model; add persistence only when this ticket explicitly requires it and test migration/reset behavior.
- Tests: add/extend dedicated Playwright coverage for `0.html` on desktop and 375×812 mobile.
