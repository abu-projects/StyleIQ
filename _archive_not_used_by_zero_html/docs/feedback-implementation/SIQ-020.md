# SIQ-020 — Deliver useful value immediately

## Ticket

- ID: SIQ-020
- Comment: Deliver useful value immediately
- Scope: Specific Screen
- Screen / Product Area: Onboarding
- Size: Medium
- Workstream: Onboarding
- Original Description: After minimal onboarding, show a useful styling result or actionable experience instead of continuing through additional setup screens.

## Problem

The current `0.html` prototype exposes this area through A-11 First-run Today, D-01/D-02, A-13 zero-Closet state. The relevant rendering/routing surface is `screens registry, renderScreen, go, onboarding, homeScreen / mirrorToday / outfitFamilies`.

Current behavior is partially represented, but the ticket acceptance is not proven end to end. The existing architecture still exposes feature-oriented routes and, where applicable, separate configuration, processing, or result states. No dedicated `0.html` regression evidence currently closes SIQ-020.

## UX Decision

- After minimal onboarding, land the user on a useful visual output or a clear first-value action.
- Do not follow account creation with several setup screens before the user sees the product.
- For zero-Closet users, show useful starter inspiration plus one simple path to add/import items.
- Measure success by time to first useful styling result.

The decision must preserve the existing editorial/liquid-material direction, reduce decisions and nested screens, and reuse canonical state rather than creating a parallel feature.

## Current Flow

`S-00 → S-01 → S-02 → A-series setup screens → A-11/D-02 first value.`

## Target Flow

`Current context → Deliver useful value immediately → immediate useful result or primary action → optional edit/sheet only when needed.`

Use a full screen only for a distinct user job. Prefer direct action, inline state, one shared bottom sheet, background work, or progressive disclosure for intermediate steps.

## Affected Screens

- Audit/change: A-11 First-run Today, D-01/D-02, A-13 zero-Closet state
- Retain until replacement passes: all existing entry, back, cancel, empty, and error paths around those screens.
- Remove/merge only after the replacement journey is verified.
- New standalone route: not assumed; first attempt to solve inside the mapped canonical surface.

## Technical Impact

- HTML/CSS/JS baseline: `0.html`
- Functions/routes: `screens registry, renderScreen, go, onboarding, homeScreen / mirrorToday / outfitFamilies`

- State: reuse the relevant canonical prototype state; do not fork Closet, Look, Canvas, Planner, Trip, Twin, Lens, or Muse data.
- Persistence: the baseline has no canonical localStorage model; add persistence only when this ticket explicitly requires it and test migration/reset behavior.
- Tests: add/extend dedicated Playwright coverage for `0.html` on desktop and 375×812 mobile.
