# SIQ-037 — Remove Prettify as a separate workflow

## Ticket

- ID: SIQ-037
- Comment: Remove Prettify as a separate workflow
- Scope: Specific Screen
- Screen / Product Area: Closet Import
- Size: Medium
- Workstream: Closet & Photo Import
- Original Description: Background cleanup and image enhancement should happen automatically rather than requiring dedicated Prettify Guide, processing, and result screens.

## Problem

The current `0.html` prototype exposes this area through B-03 Prettify guide, B-07 processing, B-08 result, L-10 Auto-Prettify. The relevant rendering/routing surface is `screens registry, renderScreen, go, importScreen / mirrorItemUpload, profileScreen / mirrorProfile`.

Current behavior is partially represented, but the ticket acceptance is not proven end to end. The existing architecture still exposes feature-oriented routes and, where applicable, separate configuration, processing, or result states. No dedicated `0.html` regression evidence currently closes SIQ-037.

## UX Decision

- Remove Prettify Guide as a required user step.
- Turn Prettifying into a local/background loading state.
- Merge the result into canonical Add/Confirm behavior.
- Keep Prettify Again only as a secondary repair tool if useful.

The decision must preserve the existing editorial/liquid-material direction, reduce decisions and nested screens, and reuse canonical state rather than creating a parallel feature.

## Current Flow

`B-01 → B-02 → B-03 → B-06 → B-07 → B-08 → B-11 → C-01.`

## Target Flow

`Current context → Remove Prettify as a separate workflow → immediate useful result or primary action → optional edit/sheet only when needed.`

Use a full screen only for a distinct user job. Prefer direct action, inline state, one shared bottom sheet, background work, or progressive disclosure for intermediate steps.
