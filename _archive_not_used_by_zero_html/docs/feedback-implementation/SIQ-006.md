# SIQ-006 — StyleIQ Lens should always be available

## Ticket

- ID: SIQ-006
- Comment: StyleIQ Lens should always be available
- Scope: General
- Screen / Product Area: Global Navigation
- Size: Medium
- Workstream: StyleIQ Lens & Visual Search
- Original Description: Provide persistent access to StyleIQ Lens from primary app surfaces so users do not need to navigate to a specific feature before using the camera.

## Problem

The current `0.html` prototype exposes this area through Root shell on D-02, C-01, I-01, K-01, L-01. The relevant rendering/routing surface is `screens registry, renderScreen, go, homeScreen / mirrorToday / outfitFamilies, closetScreen / mirrorCloset, plannerScreen / mirrorPlanner, discoverScreen / mirrorDiscover, profileScreen / mirrorProfile`.

Current behavior is partially represented, but the ticket acceptance is not proven end to end. The existing architecture still exposes feature-oriented routes and, where applicable, separate configuration, processing, or result states. No dedicated `0.html` regression evidence currently closes SIQ-006.

## UX Decision

- Expose Lens from every primary root destination without making users navigate to Discover first.
- Choose one consistent persistent access pattern that fits the current navigation and liquid-glass system.
- Do not duplicate Lens entry buttons everywhere if one global control can serve the job.
- Ensure the global entry does not hide or conflict with primary navigation actions.

The decision must preserve the existing editorial/liquid-material direction, reduce decisions and nested screens, and reuse canonical state rather than creating a parallel feature.

## Current Flow

`The screen index exposes the capability through feature-specific routes, often with separate full-screen configuration, processing, and result states.`

## Target Flow

`Current context → StyleIQ Lens should always be available → immediate useful result or primary action → optional edit/sheet only when needed.`

Use a full screen only for a distinct user job. Prefer direct action, inline state, one shared bottom sheet, background work, or progressive disclosure for intermediate steps.

## Affected Screens

- Audit/change: Root shell on D-02, C-01, I-01, K-01, L-01
- Retain until replacement passes: all existing entry, back, cancel, empty, and error paths around those screens.
- Remove/merge only after the replacement journey is verified.
- New standalone route: not assumed; first attempt to solve inside the mapped canonical surface.

## Technical Impact

- HTML/CSS/JS baseline: `0.html`
- Functions/routes: `screens registry, renderScreen, go, homeScreen / mirrorToday / outfitFamilies, closetScreen / mirrorCloset, plannerScreen / mirrorPlanner, discoverScreen / mirrorDiscover, profileScreen / mirrorProfile`
- Shared UI: `shell`, root/bottom navigation, reusable sheet/overlay patterns, image components, and accessibility labels.
- State: reuse the relevant canonical prototype state; do not fork Closet, Look, Canvas, Planner, Trip, Twin, Lens, or Muse data.
- Persistence: the baseline has no canonical localStorage model; add persistence only when this ticket explicitly requires it and test migration/reset behavior.
- Tests: add/extend dedicated Playwright coverage for `0.html` on desktop and 375×812 mobile.
