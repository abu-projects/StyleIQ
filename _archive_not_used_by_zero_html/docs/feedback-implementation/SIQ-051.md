# SIQ-051 — Move Style Twin out of required onboarding

## Ticket

- ID: SIQ-051
- Comment: Move Style Twin out of required onboarding
- Scope: Specific Screen
- Screen / Product Area: Style Twin
- Size: Medium
- Workstream: Style Twin
- Original Description: Introduce Style Twin when the user first selects Try On instead of treating virtual try-on setup as required onboarding homework.

## Problem

The current `0.html` prototype exposes this area through A-07/A-08 onboarding routes, H-01 intentional entry, L-09 settings. The relevant rendering/routing surface is `screens registry, renderScreen, go, onboarding, avatarScreen / mirrorTwinIntro / mirrorUpload, profileScreen / mirrorProfile`.

Current behavior is partially represented, but the ticket acceptance is not proven end to end. The existing architecture still exposes feature-oriented routes and, where applicable, separate configuration, processing, or result states. No dedicated `0.html` regression evidence currently closes SIQ-051.

## UX Decision

- Remove Style Twin setup from the required first-use journey.
- Trigger Style Twin when the user first chooses Try On or intentionally opens Style Twin.
- Ensure all styling features remain usable without a Twin.
- Keep optional Profile access to create/edit the Twin.

The decision must preserve the existing editorial/liquid-material direction, reduce decisions and nested screens, and reuse canonical state rather than creating a parallel feature.

## Current Flow

`A-07/A-08 or H-01 → H-02–H-09 setup → H-10 result.`

## Target Flow

`Current context → Move Style Twin out of required onboarding → immediate useful result or primary action → optional edit/sheet only when needed.`

Use a full screen only for a distinct user job. Prefer direct action, inline state, one shared bottom sheet, background work, or progressive disclosure for intermediate steps.

## Affected Screens

- Audit/change: A-07/A-08 onboarding routes, H-01 intentional entry, L-09 settings
- Retain until replacement passes: all existing entry, back, cancel, empty, and error paths around those screens.
- Remove/merge only after the replacement journey is verified.
- New standalone route: not assumed; first attempt to solve inside the mapped canonical surface.

## Technical Impact

- HTML/CSS/JS baseline: `0.html`
- Functions/routes: `screens registry, renderScreen, go, onboarding, avatarScreen / mirrorTwinIntro / mirrorUpload, profileScreen / mirrorProfile`
- Shared UI: `shell`, root/bottom navigation, reusable sheet/overlay patterns, image components, and accessibility labels.
- State: reuse the relevant canonical prototype state; do not fork Closet, Look, Canvas, Planner, Trip, Twin, Lens, or Muse data.
- Persistence: the baseline has no canonical localStorage model; add persistence only when this ticket explicitly requires it and test migration/reset behavior.
- Tests: add/extend dedicated Playwright coverage for `0.html` on desktop and 375×812 mobile.
