# SIQ-060 — Prepare next week's Looks from the recap

## Ticket

- ID: SIQ-060
- Comment: Prepare next week's Looks from the recap
- Scope: Specific Screen
- Screen / Product Area: Weekly Style Recap
- Size: Large
- Workstream: Weekly Recap & Analytics
- Original Description: Use the coming week's calendar/context to prepare relevant outfits and provide a direct next action instead of making the recap a passive analytics page.

## Problem

The current `0.html` prototype exposes this area through NEW recap → I-01 Planner / prepared Looks. The relevant rendering/routing surface is `screens registry, renderScreen, go, plannerScreen / mirrorPlanner`.

Current behavior is partially represented, but the ticket acceptance is not proven end to end. The existing architecture still exposes feature-oriented routes and, where applicable, separate configuration, processing, or result states. No dedicated `0.html` regression evidence currently closes SIQ-060.

## UX Decision

- Use upcoming Planner/calendar context to prepare suggested Looks for next week.
- Show upcoming office/social/travel contexts and a concise 'already prepared' section.
- Allow review/replace/plan actions directly from the recap.
- Do not require a separate setup flow.

The decision must preserve the existing editorial/liquid-material direction, reduce decisions and nested screens, and reuse canonical state rather than creating a parallel feature.

## Current Flow

`No dedicated recap route exists; behavior is fragmented across I-02, L-01, and M-03.`

## Target Flow

`Current context → Prepare next week's Looks from the recap → immediate useful result or primary action → optional edit/sheet only when needed.`

Use a full screen only for a distinct user job. Prefer direct action, inline state, one shared bottom sheet, background work, or progressive disclosure for intermediate steps.

## Affected Screens

- Audit/change: NEW recap → I-01 Planner / prepared Looks
- Retain until replacement passes: all existing entry, back, cancel, empty, and error paths around those screens.
- Remove/merge only after the replacement journey is verified.
- New state required: yes; it must be added to the canonical screen/state architecture, not as a duplicate feature.

## Technical Impact
