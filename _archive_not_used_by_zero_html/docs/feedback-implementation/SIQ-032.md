# SIQ-032 — Add item lifecycle statuses

## Ticket

- ID: SIQ-032
- Comment: Add item lifecycle statuses
- Scope: Specific Screen
- Screen / Product Area: Closet
- Size: Large
- Workstream: Closet & Photo Import
- Original Description: Allow every Closet item to be marked with a lifecycle or intent such as Won't Wear, Sell, Donate, Rent, Archive, or other approved terms.

## Problem

The current `0.html` prototype exposes this area through C-02 Item detail and C-04 metadata. The relevant rendering/routing surface is `screens registry, renderScreen, go, closetScreen / mirrorCloset`.

Current behavior is partially represented, but the ticket acceptance is not proven end to end. The existing architecture still exposes feature-oriented routes and, where applicable, separate configuration, processing, or result states. No dedicated `0.html` regression evidence currently closes SIQ-032.

## UX Decision

- Add lifecycle/intent status independent from garment category.
- Support approved states such as Won't Wear, Sell, Donate, Rent, Archive, and any final product wording.
- Allow status changes from Item Detail/quick actions without losing wear history or item metadata.
- Define mutual exclusivity vs multi-status rules before implementation.

The decision must preserve the existing editorial/liquid-material direction, reduce decisions and nested screens, and reuse canonical state rather than creating a parallel feature.

## Current Flow

`C-01 → C-02 → separate C-03/C-04/C-05/C-06/C-07 screens.`

## Target Flow

`Current context → Add item lifecycle statuses → immediate useful result or primary action → optional edit/sheet only when needed.`

Use a full screen only for a distinct user job. Prefer direct action, inline state, one shared bottom sheet, background work, or progressive disclosure for intermediate steps.

## Affected Screens

- Audit/change: C-02 Item detail and C-04 metadata
- Retain until replacement passes: all existing entry, back, cancel, empty, and error paths around those screens.
- Remove/merge only after the replacement journey is verified.
- New standalone route: not assumed; first attempt to solve inside the mapped canonical surface.
