# SIQ-045 — Do not make every outfit action a separate screen

## Ticket

- ID: SIQ-045
- Comment: Do not make every outfit action a separate screen
- Scope: Specific Screen
- Screen / Product Area: Outfit Actions
- Size: Foundation
- Workstream: Outfit Actions & Saved Looks
- Original Description: Save, Edit, Share, Not for Me, Swipe, Plan, and similar actions should usually happen directly around the outfit through actions, gestures, sheets, or overlays.

## Problem

The current `0.html` prototype exposes this area through E-01–E-06 plus D-04 and G-02 action entry points. The relevant rendering/routing surface is `screens registry, renderScreen, go, actionScreen, homeScreen / mirrorToday / outfitFamilies, savedScreen`.

Current behavior is partially represented, but the ticket acceptance is not proven end to end. The existing architecture still exposes feature-oriented routes and, where applicable, separate configuration, processing, or result states. No dedicated `0.html` regression evidence currently closes SIQ-045.

## UX Decision

- Audit the E-series and other outfit-action routes.
- Convert Save, Share, Dislike, Plan, Swipe, and similar behaviors into direct actions, sheets, native share, or gestures.
- Keep full screens only for tasks with meaningful standalone work, such as advanced Studio or Style Twin setup.
- Remove obsolete action routes only after all entry points are migrated.

The decision must preserve the existing editorial/liquid-material direction, reduce decisions and nested screens, and reuse canonical state rather than creating a parallel feature.

## Current Flow

`D-04/G-02 → separate E/G subroutes for save, feedback, sharing, metadata, visibility, and delete.`

## Target Flow

`Current context → Do not make every outfit action a separate screen → immediate useful result or primary action → optional edit/sheet only when needed.`

Use a full screen only for a distinct user job. Prefer direct action, inline state, one shared bottom sheet, background work, or progressive disclosure for intermediate steps.

## Affected Screens

- Audit/change: E-01–E-06 plus D-04 and G-02 action entry points
- Retain until replacement passes: all existing entry, back, cancel, empty, and error paths around those screens.
- Remove/merge only after the replacement journey is verified.
- New standalone route: not assumed; first attempt to solve inside the mapped canonical surface.

## Technical Impact

- HTML/CSS/JS baseline: `0.html`
- Functions/routes: `screens registry, renderScreen, go, actionScreen, homeScreen / mirrorToday / outfitFamilies, savedScreen`
- Shared UI: `shell`, root/bottom navigation, reusable sheet/overlay patterns, image components, and accessibility labels.
- State: reuse the relevant canonical prototype state; do not fork Closet, Look, Canvas, Planner, Trip, Twin, Lens, or Muse data.
- Persistence: the baseline has no canonical localStorage model; add persistence only when this ticket explicitly requires it and test migration/reset behavior.
- Tests: add/extend dedicated Playwright coverage for `0.html` on desktop and 375×812 mobile.
