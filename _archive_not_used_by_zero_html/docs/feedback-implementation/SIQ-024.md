# SIQ-024 — Use natural language instead of technical forms

## Ticket

- ID: SIQ-024
- Comment: Use natural language instead of technical forms
- Scope: General
- Screen / Product Area: Whole Product
- Size: Foundation
- Workstream: Product Simplification Foundation
- Original Description: Where possible, let users explain what they want naturally and allow StyleIQ to structure the information in the background.

## Problem

The current `0.html` prototype exposes this area through M-01 Muse, I-03/I-04 Planner, J-01/J-02 Trips, Lens intent entry. The relevant rendering/routing surface is `screens registry, renderScreen, go, museScreen / enrichCoreScreens, plannerScreen / mirrorPlanner, tripScreenV2`.

Current behavior is partially represented, but the ticket acceptance is not proven end to end. The existing architecture still exposes feature-oriented routes and, where applicable, separate configuration, processing, or result states. No dedicated `0.html` regression evidence currently closes SIQ-024.

## UX Decision

- Prioritize intent capture in Planner, Trips, Muse, shopping decisions, and outfit modification.
- Let StyleIQ parse a user sentence into structured internal fields.
- Expose structured fields only as optional edit/review controls.
- Keep deterministic prototype behavior clear where real AI parsing is not implemented.

The decision must preserve the existing editorial/liquid-material direction, reduce decisions and nested screens, and reuse canonical state rather than creating a parallel feature.

## Current Flow

`The screen index exposes the capability through feature-specific routes, often with separate full-screen configuration, processing, and result states.`

## Target Flow

`Current context → Use natural language instead of technical forms → immediate useful result or primary action → optional edit/sheet only when needed.`

Use a full screen only for a distinct user job. Prefer direct action, inline state, one shared bottom sheet, background work, or progressive disclosure for intermediate steps.

## Affected Screens

- Audit/change: M-01 Muse, I-03/I-04 Planner, J-01/J-02 Trips, Lens intent entry
- Retain until replacement passes: all existing entry, back, cancel, empty, and error paths around those screens.
- Remove/merge only after the replacement journey is verified.
- New standalone route: not assumed; first attempt to solve inside the mapped canonical surface.

## Technical Impact

- HTML/CSS/JS baseline: `0.html`
- Functions/routes: `screens registry, renderScreen, go, museScreen / enrichCoreScreens, plannerScreen / mirrorPlanner, tripScreenV2`
- Shared UI: `shell`, root/bottom navigation, reusable sheet/overlay patterns, image components, and accessibility labels.
- State: reuse the relevant canonical prototype state; do not fork Closet, Look, Canvas, Planner, Trip, Twin, Lens, or Muse data.
- Persistence: the baseline has no canonical localStorage model; add persistence only when this ticket explicitly requires it and test migration/reset behavior.
- Tests: add/extend dedicated Playwright coverage for `0.html` on desktop and 375×812 mobile.
